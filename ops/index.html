HITL gates

A human-in-the-loop gate is written into the plan before the work runs, with five fields:

  1. Who: one named reviewer (the owner, a Cursor GO, a lane lead, or all hands).
  2. What: the exact artifact (a pull request and its head SHA, a demo URL, a config change, a merge, live keys).
  3. When: before merge, before deploy, before live keys, before anything customer-facing.
  4. How: GO or NO-GO on the board, or the work marked waiting on the gate. Chat alone is not a verdict.
  5. Timeout: silence past the window means hold, never auto-advance.

Always gated: anything irreversible, customer-visible, spendy, identity-bearing, or on live keys and production.

Delivery mechanisms M1–M8

  1. M1 Severity gates: a P1 finding blocks; P2 and below are fixed when cheap, otherwise tracked as follow-ups.
  2. M2 Two-round stop: after two review rounds, remaining non-blocking findings become follow-ups and the pull request ships.
  3. M3 Auto-merge on green: reserved for the owner; not adopted.
  4. M4 Size cap: 400 lines as guidance, ranked below M5.
  5. M5 One owner per work item: claimed atomically and visibly before work begins.
  6. M6 Close on a repository read: a work item closes when the repository shows it, never on a report.
  7. M7 A check must be able to fail: every guard is mutation-tested; a guard whose removal changes nothing is deleted.
  8. M8 Reviews bound to a SHA: a review of an older head neither approves nor blocks the new one.
